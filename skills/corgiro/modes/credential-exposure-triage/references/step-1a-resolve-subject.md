# Step 1a — Resolve Subject(s)

**Inputs:** subject parameters from MODE.md; the Roster (`~/.corgiro/state/roster.json`); the pre-flight result.

**Allowed calls** (all read-only; dispatch per [`../../../references/credential-resolution.md`](../../../references/credential-resolution.md) on the owning account's Roster Entry `via`). The raw key comes from the subject's `$COMPROMISED_ACCESS_KEY_ID_N` env var (operator subject) or the in-memory key map (hop/derived); it is never read from a persisted file:
- `aws sts get-access-key-info --access-key-id="$COMPROMISED_ACCESS_KEY_ID_N"` — returns the owning account ID; it may be called from **any session that grants `sts:GetAccessKeyInfo`** (the owner is returned regardless of the caller's account), per the two-stage Resolve order below. `AKIA…` = long-term IAM-user or root credentials; `ASIA…` = temporary STS credentials. It says nothing about key state. Source: [GetAccessKeyInfo](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetAccessKeyInfo.html).
- For an `AKIA` subject, once the owning account is a reachable Roster Entry and you have a session in it:
  - `aws iam get-access-key-last-used --access-key-id="$COMPROMISED_ACCESS_KEY_ID_N"` → `UserName`, `LastUsedDate`, `ServiceName`, `Region`. **Validate the returned `UserName`** with `re.fullmatch` body `[A-Za-z0-9][A-Za-z0-9_+=.@-]{0,63}` (ASCII, first char alphanumeric, no comma/newline; see the regex-dialect note in MODE.md) before using it in any later call. `LastUsedDate` is a **current best-effort snapshot**, not a history; IAM has tracked last-used information since 2015-04-22, and this API documents the returned fields but no specific update latency or granularity — do not assume a bound. Source: [AccessKeyLastUsed API reference](https://docs.aws.amazon.com/IAM/latest/APIReference/API_AccessKeyLastUsed.html).
  - `aws iam list-access-keys --user-name=<validated name>` (all keys on the principal), `list-attached-user-policies`, `list-user-policies`, `list-groups-for-user` (+ each group's `list-attached-group-policies` / `list-group-policies`), `get-login-profile`, `list-mfa-devices` (each with the user name equals-joined and validated by the same regex).
- `aws iam list-attached-user-policies` / `list-attached-role-policies` on the principal to detect `AWSCompromisedKeyQuarantineV2`/`V3` ([V2](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSCompromisedKeyQuarantineV2.html), [V3](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSCompromisedKeyQuarantineV3.html)); record in `subjects.json.quarantine_policy`.

**Resolve order (non-circular):**
1. **Get the owning account.** `sts get-access-key-info` returns the owner of the key **regardless of which account the caller is in**, so call it from whichever session can: the operator base session if it has `sts:GetAccessKeyInfo`, otherwise **any one reachable member Roster Entry session** (an `assume-role` session or an SSO per-account profile — all include `sts:GetAccessKeyInfo` under `CorgiroReadOnlyRole`/`SecurityAudit`). The tooling operator role under `cross-account-role` typically lacks it; that is fine because a member session supplies it. If **no** reachable session grants `sts:GetAccessKeyInfo` (e.g. `ViewOnlyAccess` everywhere), require an operator-supplied `account_id`, or a GuardDuty/Health subject that already carries the account; a raw-key-only subject with no resolvable account stops as `unresolved-account`.
2. If the owning account is **not** a reachable Roster Entry → stop this subject with `account-outside-roster` (Corgiro cannot trace into an account it cannot reach). Record and continue with other subjects.
3. Otherwise acquire that account's Roster Entry session and run the `AKIA` IAM calls above **in that account**.

**Dual Access Mode:**
- `cross-account-role` — the owning account is learned first (Resolve order step 1, from any session granting `sts:GetAccessKeyInfo`); the per-principal IAM reads then run in that owning account's `assume-role` Roster Entry session, never from the tooling account (which has no `sts:GetAccessKeyInfo` / `iam:*` on members).
- `identity-center-direct` with `SecurityAudit` — same two-stage order via the per-account SSO profile.
- `identity-center-direct` with `ViewOnlyAccess` — `sts:GetAccessKeyInfo` and `iam:GetAccessKeyLastUsed` are **not** granted; the operator must supply the owning `account_id` and the IAM user/role `name`, and `last_used` is recorded `not-observable`. Degrade, do not fail (MODE.md Prerequisites).

**Two-stage rule (restated so no step reads the owning account before it is known):** (1) learn the owning account via `sts get-access-key-info` from any granting session, or an operator-supplied `account_id` / a GuardDuty-Health subject that carries it; (2) only then acquire that account's Roster Entry session and run the owning-account IAM reads there. No instruction runs an owning-account read before stage 1 returns the account.

**Subject-kind handling:**
- `guardduty-finding` / `health-event` — the Step 0 resolve call(s) already produced the account + principal (GuardDuty: `get-findings`; Health: `describe-event-details` + `describe-affected-entities`). For a Health event, set `key_status: valid` and use `entityValue` as the key **only if** it matched `re.fullmatch` body `(AKIA|ASIA)[0-9A-Z]{16}`; otherwise set `key: null`, `key_status: candidate-rejected` (a non-key `entityValue` was returned) or `not-observable` (no entity), and **forbid fan-out** for this subject until the operator supplies a valid `access_key_id`. Populate `subjects.json` accordingly, then run the `AKIA` IAM reads only when `key_status: valid` and the key is `AKIA`.
- `role-session` (`role_arn` + `session_name` + `account_id`) — the account is given; record the role as the subject principal (`principal.type: AssumedRole`, `principal.arn: role_arn`, `principal.name`: the role name, i.e. the segment after `role/`) **and** persist the validated inputs in the subject's own fields: `role_arn` (validated with the role-ARN body in [`step-7-report-handoff.md`](step-7-report-handoff.md) → "Per-type substitution regexes") and `session_name` (body `[A-Za-z0-9][A-Za-z0-9_+=.@-]{1,63}`). There is no access key, so `key: null`, `key_status: not-observable`. This subject is the **exemption** from the key-validity fan-out ban (MODE.md "Key validity gate"; restated in [`state-contract.md`](state-contract.md)): it runs **Step 4 only**, by `Username=<subjects.json.session_name>` (not an `AccessKeyId` lookup and not the role name), with `target-plan.json.lookup_attribute: Username` and `value_source: subject.session_name` — see the role-session path in [`step-4-cloudtrail-timeline.md`](step-4-cloudtrail-timeline.md). STILL ACTIVE for it matches `role_arn` + `session_name` (Step 6e), not a key fingerprint.
- Bare `ASIA` with no role/account/time — best-effort: Step 4 searches for any event made with it and derives the role/session from that event's `userIdentity`; if none is found, mark the subject `unresolved`. An `ASIA` key cannot be traced to its issuing STS event by an `AccessKeyId` lookup.

**Hard stops:**
- Never print or persist the raw key (MODE.md Safety) — populate `key` as `{masked, sha256}`.
- Wording for authorization: record "identity-policy grants observed; effective authorization not determined" — SCPs, permission boundaries, session/resource policies, and explicit denies are **not** visible from these calls.
- Do **not** here run the `ResourceName=<principal>` CloudTrail search for events done *to* the principal: that lookup feeds API output into a command and is gated. It runs in **Step 4** (after the Step 2 gate) with the IAM-name regex, not in Step 1.

**Output:** `subjects.json` per [`state-contract.md`](state-contract.md). One entry per subject, with `status` set. Partial resolution (account known, name unknown under ViewOnlyAccess) is `degraded-view-only`, not an error.
