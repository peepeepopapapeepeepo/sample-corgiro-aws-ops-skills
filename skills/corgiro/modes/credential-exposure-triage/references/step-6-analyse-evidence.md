# Step 6 — Analyse Evidence (client-side; no new AWS calls except budgeted follow-ups)

Classify the fetched evidence entirely client-side over the persisted `timeline/*`, `signals.json`, and `sessions.json`. The only AWS calls here are the budgeted lifecycle follow-ups in 6b (static table, ID-only substitution). Outputs `findings.json` + `completeness.json` (schemas in [`state-contract.md`](state-contract.md)).

**Classification precedence:** the exact event-catalog tuple takes precedence over `readOnly`; classify unmatched `readOnly=true` events as generic Discovery only.

## 6a — Bucket classification
Assign a bucket **only** on an exact `(eventSource, eventName)` match in [`event-catalog.md`](event-catalog.md) — **no prefix matching**. Buckets follow GuardDuty's tactic taxonomy: `Discovery | InitialAccess | CredentialAccess | Persistence | PrivilegeEscalation | DefenseEvasion | Exfiltration | Impact | ResourceAbuse`. An event matched to no tuple but carrying `readOnly=true` is generic `Discovery`. An event whose `(source, eventName, predicate)` matches a row of the catalog's separate **"Audit records"** table (e.g. `PutBucketVersioning` with `Status=Enabled`) is written to `completeness.json.audit_records[]` as a neutral entry — it is **not** a finding, gets no bucket, and never becomes a Risk Tier. Each classified event also gets `outcome` (succeeded | attempted) and `confidence` (confirmed | observed-attempt | inferred | not-observable | partial).

## 6b — Lifecycle pairing (budgeted read-only follow-ups)
Pair each **create** event with its **delete** event using the explicit `(source, create eventName, delete pair eventName, pair key)` rows in the static lifecycle table in [`event-catalog.md`](event-catalog.md) — matching on the row's pair-key field, never by prefix or wildcard — to decide "created, still live" vs "created then deleted (staging)". Within `call_budget`, confirm live state with that same table's read-only follow-up argv, substituting only the resource ID validated by the row's regex column. **Each argv is one AWS request and one counted call:** a follow-up is issued with `--no-paginate` and never loops on a token (a truncated first page is recorded as `partial`, not paged), and a **multi-command row** (snapshot `describe-snapshots` + `describe-snapshot-attribute`; Lambda `list-functions` + `get-policy`) **decrements both counters (`call_budget` and `global_call_budget`) before each argv** — never one decrement for the pair. Examples the table encodes (each cited there): `kms describe-key`, `ec2 describe-snapshots --owner-ids self` + `describe-snapshot-attribute --attribute createVolumePermission` (two requests), `ec2 describe-iam-instance-profile-associations`, `ssm list-commands` with a `--query` projection of metadata only (CommandId/DocumentName/Status/RequestedDateTime/InstanceIds — **never** `Parameters`; never `get-command-invocation` output), `lambda list-functions --query 'Functions[].[FunctionName,FunctionArn]'` (names/ARNs only — never env vars) + `get-policy` (two requests; `GetFunction`/`GetFunctionConfiguration` are denied by the member role), `logs describe-log-streams` (timestamps only — `FilterLogEvents`/`GetLogEvents` denied), `cloudformation describe-stacks` (StackSet enumeration needs delegated-admin authority; else not observable), `iam get-user`/`get-role`/`get-policy`, `cloudtrail get-event-selectors` (does any trail log S3 data events?). **Every lifecycle row MUST define source, create event name, delete pair event name, success predicate, resource-ID JSON path, pair key, account/Region source, and follow-up argv template; missing fields prohibit pairing and follow-up.**

> The `cloudformation describe-stacks` follow-up confirms a single stack. **Organization-wide StackSet health is not observable** from a normal member/tooling session (StackSet enumeration needs management / delegated-admin authority); mark it not observable rather than claiming coverage.

> **Follow-ups never substitute a raw key.** Any follow-up that would key on an access key ID (e.g. confirming a created key is live) uses `iam list-access-keys --user-name=<validated name> --no-paginate` and matches the target by `sha256` against the masked key — a masked `AKIA****XXXX` cannot be passed to `--access-key-id` and no raw value is persisted to substitute (MODE.md Safety). Raw hop/derived keys needed for a *Step 4* timeline come from the in-memory key map, never from a persisted file.

> **A denied follow-up is recorded, never retried or worked around.** If a 6b/6c follow-up returns `AccessDenied` (under `ViewOnlyAccess` this is expected for `iam get-user`/`get-role`/`get-policy`/`get-policy-version`, `kms describe-key`, `cloudtrail get-event-selectors`, and `ssm list-commands`, none of which that policy grants — [ViewOnlyAccess](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/ViewOnlyAccess.html)), set that finding's `lifecycle.state` (or `lockout[].current_state`) to `unknown`, add the denied action to `completeness.json.coverage.signals_unavailable`, and continue — the call still counted against both budgets. Classification proceeds on the CloudTrail evidence alone.

## 6c — Lockout analysis
Identify IAM events whose **target principal is a legitimate principal** — i.e. **not** the subject's own principal and **not** a principal proven attacker-created on `sessions.json.watchlist_principals` (that list holds only principals created by a successful `CreateUser`/`CreateRole`; a login/instance profile on a pre-existing user does **not** put it on the list, so a genuine lockout of a pre-existing user is never hidden). For each such `PutUserPolicy` / `PutRolePolicy` / `AttachUserPolicy` / `AttachRolePolicy` / `DetachUserPolicy` / `UpdateAssumeRolePolicy` / `DeleteLoginProfile` / `UpdateAccessKey(Inactive)` event:
- For an **inline**-policy event (`PutUserPolicy`/`PutRolePolicy`), parse the event's `requestParameters.policyDocument` for `"Effect":"Deny"`.
- For a **managed**-policy `Attach*` event there is no inline document in the event; record the attached `policyArn` and, within budget, resolve it with the lockout follow-up table rows below (`iam get-policy` + `iam get-policy-version`).
- Confirm current state within budget using the lockout follow-up rows (login profile, inline/attached policies, trust policy, key status). The target name is validated against its row regex (below) before any follow-up.

Produce a table of locked-out legitimate principals with reversal **guidance**. Reversal text is mutating guidance, so it goes in `containment.md` (not run by Corgiro) and never interpolates an attacker-controlled free-text field — only the regex-validated principal name. Attacker-targeted StackSet execution roles are flagged by name match against the member role's StackSet-managed naming (`StackSet-*` / the operator's configured prefix); Corgiro's own role is StackSet-managed, so its appearance as a target is called out.

**Lockout follow-up rows** (read-only; ID-only substitution; same gate and both budget counters as 6b; **each argv is one counted request — a two-command row such as `list-attached-user-policies` + `list-user-policies`, or `get-policy` + `get-policy-version`, decrements both counters before each command**; options use the `--opt=<ID>` equals-joined form so a validated value can never be read as a flag):

| target eventName | read-only follow-up (argv, equals-joined, `--no-paginate`) | ID JSON path | ID regex (`re.fullmatch` body; first char alphanumeric, no comma/newline) |
|---|---|---|---|
| PutUserPolicy / AttachUserPolicy / DetachUserPolicy | `iam list-attached-user-policies --user-name=<ID> --no-paginate` then `iam list-user-policies --user-name=<ID> --no-paginate` | `requestParameters.userName` | `[A-Za-z0-9][A-Za-z0-9_+=.@-]{0,63}` |
| AttachUserPolicy / AttachRolePolicy (managed) | `iam get-policy --policy-arn=<ID>` then `iam get-policy-version --policy-arn=<ID> --version-id=<v from get-policy>` | `requestParameters.policyArn` | `POLICY_ARN` (named body defined directly below this table) |
| PutRolePolicy / UpdateAssumeRolePolicy | `iam get-role --role-name=<ID>` | `requestParameters.roleName` | `[A-Za-z0-9][A-Za-z0-9_+=.@-]{0,63}` |
| DeleteLoginProfile | `iam get-login-profile --user-name=<ID>` | `requestParameters.userName` | `[A-Za-z0-9][A-Za-z0-9_+=.@-]{0,63}` |
| UpdateAccessKey (targeting another principal) | `iam list-access-keys --user-name=<ID> --no-paginate` (match the affected key by sha256) | `requestParameters.userName` | `[A-Za-z0-9][A-Za-z0-9_+=.@-]{0,63}` |

`POLICY_ARN` (a `re.fullmatch` body; defined outside the table because a `|` inside a table cell splits the cell under GFM): `arn:aws[a-z-]*:iam::(aws|[0-9]{12}):policy/[A-Za-z0-9][A-Za-z0-9_+=,.@/-]{0,127}` — the account segment is either the literal `aws` (AWS managed policy) or a 12-digit account ID.

## 6d — IP / user-agent pivot
Build a client-side index of `sourceIPAddress` / `userAgent` across **all** fetched events (all subjects): which principals were seen from each IP, for operator attribution. There is **no** server-side IP lookup attribute in `lookup-events` ([LookupAttribute](https://docs.aws.amazon.com/awscloudtrail/latest/APIReference/API_LookupAttribute.html) lists no IP key) — say so and point to CloudTrail Lake / Athena (Step 7 handoff). Sanitize every `userAgent`/IP string before it reaches the report.

## 6e — STILL ACTIVE
Per subject, STILL ACTIVE counts **only** events the subject itself performed, drawn from primary-search pages only (`search: "primary"`), never from supplemental `ResourceName` / instance-session `Username` pages (those are actions done *to* the principal, including the operator's own post-containment `UpdateAccessKey(Inactive)`, and must not raise a false positive). For a **key subject**, "the subject itself" means events whose `userIdentity.accessKeyId` sha256 **equals the subject fingerprint**.

> **Role-session subjects.** A role-session subject has no single long-lived `accessKeyId` fingerprint; its identity is `subjects.json.role_arn` **plus** `subjects.json.session_name` (both operator-supplied and validated in Step 1a). Its primary pages are the Step 4 role-session lookups — **both** the `Username=<session name>` attempt and the `Username=<role name>` fallback — each already filtered to `userIdentity.sessionContext.sessionIssuer.arn == role_arn` and tagged `search: "primary"`. For such a subject, STILL ACTIVE counts events on those primary pages whose `sessionIssuer.arn` equals `role_arn` **and** whose session name — the last `/`-separated segment of `userIdentity.arn` (`arn:aws:sts::<acct>:assumed-role/<role>/<session>`) — equals `session_name` ([user-identity reference](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html)). **If both Step 4 attempts returned zero kept events, the subject's activity is `not-observable` (Event history may not index the session under either `Username` value), never reported as "no activity" or an all-clear.** The `get-access-key-last-used` clause below does not apply to it (no key).

If that latest subject-actor event time, or the `get-access-key-last-used` snapshot (a **current best-effort snapshot**; the API returns no freshness guarantee — [get_access_key_last_used](https://docs.aws.amazon.com/IAM/latest/APIReference/API_GetAccessKeyLastUsed.html)), is later than `--contained-at`, raise `STILL ACTIVE — containment incomplete` at the top of the terminal and report. **Route to the root runbook only from an event for this subject with `userIdentity.type=Root`. A post-containment event confirms STILL ACTIVE; last-used data alone means possible activity.**

## 6f — Root detection + quarantine
Root is confirmed only by `userIdentity.type == Root` on a resolved event, or a credential-report root row with an active key (Step 0 branch E). Record whether `AWSCompromisedKeyQuarantineV2`/`V3` is attached (from Step 1a).

## 6g — Containment-defeating events (Critical)
Mark `containment_defeating: true` for: `UpdateAccessKey` reactivating a key; `DetachUserPolicy`/`DetachRolePolicy` targeting `AWSCompromisedKeyQuarantine*`; `UpdateAccountPasswordPolicy`/`DeleteAccountPasswordPolicy`. These are Critical regardless of other activity.

**Hard stops:** no bucket without an exact tuple; data events (S3 object reads, Lambda `Invoke`, DynamoDB item ops) are `not-observable`, never "none"; record `data_event_blind_spots` and `signals_unavailable` in `completeness.json`. **Budget (both counters, pre-call):** every 6b/6c follow-up decrements both `call_budget` (its account) and `global_call_budget` before the call; stop the account at the per-account cap (`partial — call budget exhausted`) and the whole run before a call that would exceed `global_call_budget` (`partial — global call budget exhausted`, recorded in `completeness.json`) — classification continues on the evidence already gathered.

**Output:** `findings.json` + `completeness.json`.
