# Step 1b — Discover Candidates (discovery path, no subject supplied)

When no subject is given, rank suspect credentials from exposure signals, then let the operator pick subjects for the targeted path. **Gate first:** write `discovery-plan.json` (accounts, regions, which signals, call estimate) and present the plan gate per [`../../../references/sweep-plan-coverage.md`](../../../references/sweep-plan-coverage.md) **before any fan-out**.

**Inputs:** Roster; `expected_regions` (authoritative footprint; default config `defaultRegions`); `accounts`/`regions` if the operator scoped them. If `defaultRegions` is `auto` or unset and `account list-regions` is unavailable (e.g. `identity-center-direct`), ask the operator for the region footprint once (and offer to save it), per [`../../../references/sweep-plan-coverage.md`](../../../references/sweep-plan-coverage.md) → "Planning a sweep"; otherwise fall back to the shared `fallbackRegions`.

**Signals, cheapest and most certain first:**

### Signal 0 — AWS Health credential-exposure events (always; near-certain; may identify the key)
- `aws health describe-event-types --region us-east-1` **unfiltered**, paginated; match `eventTypeCode` **client-side** against `CREDENTIALS`. Never hardcode `AWS_RISK_CREDENTIALS_*` and never pass a `RISK` service filter — the code set changes. Source: [describe-event-types](https://docs.aws.amazon.com/cli/latest/reference/health/describe-event-types.html) (unfiltered returns all event types).
- Then pull matching events: `describe-events-for-organization` (entitled org) ([ref](https://docs.aws.amazon.com/cli/latest/reference/health/describe-events-for-organization.html)) or per-account `describe-events`. The affected entity is **not** returned by `describe-event-details` (description only — [DescribeEventDetails](https://docs.aws.amazon.com/health/latest/APIReference/API_DescribeEventDetails.html)); call `describe-affected-entities --filter '{"eventArns":["<arn>"]}'` ([DescribeAffectedEntities](https://docs.aws.amazon.com/health/latest/APIReference/API_DescribeAffectedEntities.html)), whose `entities[].entityValue` the API documents only as "the ID of the affected entity". Treat `entityValue` as a **candidate**: use it as the suspect key only if it matches `re.fullmatch` body `(AKIA|ASIA)[0-9A-Z]{16}`; otherwise record the key `not-observable` for that event and require an operator-supplied key before a targeted run. Skip an account on `SubscriptionRequiredException`.
- **Health is global with its active endpoint in `us-east-1` and passive failover in `us-east-2`** ([Health API multi-Region](https://docs.aws.amazon.com/health/latest/ug/health-api.html)); if the `us-east-1` calls fail during an impairment, retry against `us-east-2`.

### Signal 1 — GuardDuty AccessKey-type findings (if present; dual path; near-certain for compromised-credential types)
- Per the dual Access Mode path in [`step-3-collect-signals.md`](step-3-collect-signals.md). Keep **every** finding type (no type filter on the targeted path). The IAM compromised-credential types (resource type `AccessKey`) are the high-signal ones — e.g. the `CredentialAccess:IAMUser/*` family. **`AttackSequence:IAM/CompromisedCredentials` is selected by an exact `type` criterion, not by `resourceType`** (the attack-sequence finding does not document an `AccessKey` resource type), so the discovery path issues **two `list-findings` per detector** (`resource.resourceType = AccessKey`, then `type = AttackSequence:IAM/CompromisedCredentials`; exact commands in Step 3) and the `discovery-plan.json` estimate counts both. Verify exact type strings at run time against [GuardDuty IAM finding types](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_finding-types-iam.html) and [attack-sequence finding types](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty-attack-sequence-finding-types.html); the catalog does not assert the full type list from memory.
- Missing detector in an account → finding "no GuardDuty detection coverage in account X" (Informational + recommendation), never silence.

### Signal 2 — IAM credential report (always; cheap; hygiene, not detection)
- `aws iam generate-credential-report` then `aws iam get-credential-report` per account (as [`iam-security-review`](../../iam-security-review/MODE.md) Step 3). `generate-credential-report` is **asynchronous** and carries the `State` field: poll `aws iam generate-credential-report` until its `State` is `COMPLETE` ([GenerateCredentialReport](https://docs.aws.amazon.com/IAM/latest/APIReference/API_GenerateCredentialReport.html)) with short backoff, **bounded to a few polls per account** (counted against the budget), then call `get-credential-report` **once** and base64-decode its `Content` ([GetCredentialReport](https://docs.aws.amazon.com/IAM/latest/APIReference/API_GetCredentialReport.html) has no `State` field and fails with `ReportInProgress` while generating); if `State` is not `COMPLETE` after the bound, record `credential_report.collected: false` and move on. The report is a single point-in-time snapshot (so no "dormant then active" or "first password use" inference), covers **every** key per user — "Users can have up to two access keys", in the `access_key_1`/`access_key_2` columns ([getting-credential-reports](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_getting-report.html)) — and contains **no access key IDs** (nothing to mask). Confirm staleness/column names at run time per [getting-credential-reports](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_getting-report.html); do not assert staleness figures from memory.
- Flag: `last_used_region` outside `expected_regions` (allowlist `us-east-1` for IAM/STS and `N/A` for non-regional services); an active root key (regardless of use); old unrotated keys with recent use; console users without MFA. For each flagged user: `list-access-keys --user-name` then `get-access-key-last-used` per key.
- Payer-only Cost Explorer anomalies (`ce get-anomalies`, `ce get-cost-and-usage` by region+service) as account-level context when the caller is the payer; unavailable to a non-payer setup.

### Signal 3 — opt-in, gated, visibly partial sample
Only when the operator opts in and only in named account/region pairs (`lookup-events` is newest-first and page-capped, so this is a sample, not a scan):
- one page of `lookup-events --lookup-attributes AttributeKey=EventSource,AttributeValue=iam.amazonaws.com` in `us-east-1` (all IAM mutations, one region),
- one page of `AttributeKey=Username,AttributeValue=root` in **each of `us-east-1`, `us-east-2`, and `us-west-2`** — root `ConsoleLogin` is recorded in one of those three Regions, so a us-east-1-only sample can miss it ([console sign-in events](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-aws-console-sign-in-events.html)),
- one page each for ~20 rare high-signal `EventName`s from [`event-catalog.md`](event-catalog.md) ("Signal-3 high-signal EventNames").
Group results by `userIdentity.accessKeyId` for **every** identity type (stolen instance creds appear as `AssumedRole`). **Report coverage by the earliest event returned**, never as a 7-day scan. The sample does not widen its time window: under a page cap, widening would re-return the newest events as observed duplicates rather than reaching older ones. Valid `LookupAttributeKey` values per [LookupAttribute](https://docs.aws.amazon.com/awscloudtrail/latest/APIReference/API_LookupAttribute.html).

**Output:** a ranked suspect table — masked key, owner, account, signals fired, first-seen, why, confidence — and `discovery-plan.json`. The operator picks subjects, which become the targeted path (Step 1a resolves them, Steps 2-7 run).

**If the operator picks no subject (or every signal is empty), the discovery path still produces output** — it does not dead-end:
- Write `discovery-result.json` (the ranked suspects, masked) and `findings.json` containing the **coverage-gap findings** (every "no GuardDuty detection coverage in account X region R", any Health-subscription gaps, any Signal-3 partiality) plus `completeness.json`.
- Render a **Discovery Result report** `Credential-Exposure-Discovery-<DATE>.{md,html}` via [`../../../references/report-format.md`](../../../references/report-format.md): the suspect table, the signals/coverage section, and Methodology. If every signal was empty, the report states `no exposure signal observed; detection coverage: <list>` — **never an all-clear** (Risk Tier Informational, `badge--zinc`). This is the home for the coverage-gap findings when no targeted run follows.

**Hard stops:** gate before fan-out; GuardDuty across many accounts × regions is expensive on `identity-center-direct` (see Step 3) — require named scope or a separate high-cost approval in the gate.
